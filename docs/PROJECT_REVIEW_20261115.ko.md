## 3. 발견 사항

### 3.1. 현재 가상환경에서 구형 스크립트 일부가 시작부터 실패한다

**분류:** 실행 환경의 의존성 누락

현재 가상환경에는 `xgboost`, `imbalanced-learn`, `skorch`가 설치되어 있지 않다. 시작 또는 import 단계에서 다음 실패를 확인한다.

| 파일 | 확인된 직접 실패 원인 |
|---|---|
| [`main.py`](../main.py) | `ModuleNotFoundError: No module named 'xgboost'` |
| [`column_study.py`](../column_study.py) | `src.optimization`을 통해 XGBoost를 import하다 실패 |
| [`ensemble_study.py`](../ensemble_study.py) | XGBoost import 실패 |
| [`target_encoding_study.py`](../target_encoding_study.py) | XGBoost import 실패 |
| [`evaluate_cv.py`](../evaluate_cv.py) | `ModuleNotFoundError: No module named 'imblearn'` |
| [`resampling_study.py`](../resampling_study.py) | imbalanced-learn import 실패 |

`skorch`의 미설치는 패키지 메타데이터로 확인한 사항이며, 위 여섯 파일의 직접 실패 원인과는 구분한다.

구형 의존성은 [`requirements.txt`](../requirements.txt)에 명시되어 있다. 따라서 위 실패를 코드 자체의 결함으로 단정해서는 안 된다. 현재 PyTorch도 고정 버전인 2.2.1과 다른 2.15.0이므로, 전체 구형 환경을 재현하려면 버전 차이까지 고려해야 한다.

**권장 조치:** 구형 워크플로의 의존성을 별도 환경에 설치하고 다시 실행한다. 현재 베이스라인과 개선 실험에 필요한 의존성과 구분해 관리한다.

### 3.2. 설정을 바꿔도 기존 GAIN 캐시를 그대로 사용한다

**분류:** 코드 동작 문제 · 우선 수정 권장

위치: [`build_cache.py`](../build_cache.py)의 `_is_complete()` 및 `ensure_cache()` — 점검 당시 55행, 72행 부근

`ensure_cache()`는 기존 파일에 필수 키가 있는지만 확인한다. 다음 변경 사항은 검사하지 않는다.

- 인코딩할 열 목록
- GAIN 반복 횟수
- 원본 학습·테스트 데이터
- 전처리 및 특성 생성 코드

필수 키를 가진 임시 캐시를 만든 뒤 다른 인코딩 열과 반복 횟수를 전달해도, 재생성 없이 기존 캐시가 반환되는 것을 재현한다.

이 경우 사용자는 설정을 변경했다고 생각하지만 실제로는 이전 설정의 행렬로 실험할 수 있다. 원본 데이터가 교체되어도 오래된 행렬을 재사용할 수 있다.

**권장 조치:** 캐시에 입력 데이터 해시, 관련 소스 해시, 인코딩 열, 반복 횟수 등 생성 메타데이터를 기록하고, 요청 조건과 일치할 때만 재사용한다.

### 3.3. `--variants`의 순서를 바꾸면 실험 도중 종료된다

**분류:** 코드 동작 문제

위치: [`improve_cv.py`](../improve_cv.py)의 옵션 검증 및 `run_variant()` — 점검 당시 296행, 245행 부근

다음 옵션은 시작 시 검증을 통과하지만 실행 도중 실패한다.

```bash
python improve_cv.py --sample 100 --estimators 1 --trials 1 \
  --variants baseline,blend,lgb_tuned,catboost \
  --output-dir /tmp/ivf-project-audit-20261115
```

```text
KeyError: 'lgb_tuned'
```

옵션 검증은 `lgb_tuned`와 `catboost`가 목록에 포함되어 있는지만 확인한다. `blend`보다 먼저 실행되었는지는 검사하지 않아, 아직 생성되지 않은 예측값을 참조한다. 기본 실행 순서는 정상이다.

**권장 조치:** 의존 모델을 먼저 실행하도록 순서를 정규화하거나, 잘못된 순서를 학습 시작 전에 거부한다.

### 3.4. GAIN의 최종 대체 단계가 학습 모드로 실행된다

**분류:** 추론 동작 검토 필요

위치: [`src/gain_imputer.py`](../src/gain_imputer.py)의 최종 대체 단계 — 점검 당시 225~231행 부근

최종 출력 전에 `G.eval()`을 호출하지 않는다. 작은 입력으로 실행하고 마지막 forward 상태를 확인한 결과는 다음과 같다.

```text
training=True, grad_enabled=False
```

`torch.no_grad()`는 기울기 계산을 끄지만 모델을 평가 모드로 바꾸지는 않는다. 따라서 최종 대체 단계에도 Dropout과 BatchNorm의 학습 모드 동작이 적용된다.

작은 입력에서는 유한한 출력과 관측값 보존을 확인한다. 이 결과만으로 일반적인 평가 모드 추론과 동작이 같다고 볼 수는 없다.

**권장 조치:** 최종 대체 전에 `G.eval()`을 적용하고, 관측값 보존과 출력의 유효성을 다시 확인한다. 추론 시 확률적 Dropout을 의도한 설계라면 그 목적과 평가 방법을 명시한다.

### 3.5. README가 GAIN 실험에서 확인하지 않은 원인까지 단정한다

**분류:** 문맥·근거 오류 · 우선 수정 권장

위치: [`README.ko.md`](../README.ko.md)의 5-6 및 8-4 — 점검 당시 278~279행, 443~444행 부근. [`README.md`](../README.md)에도 같은 취지의 설명이 있다.

README는 GAIN의 손해가 대체 방법 자체가 아니라 분할 전에 타깃까지 넣어 학습한 누수 때문이었다고 단정한다.

그러나 fold 안에서 학습한 GAIN과 다른 방법의 통제 비교는 아직 수행하지 않았다. [`docs/experiments/IMPROVEMENT.md`](experiments/IMPROVEMENT.md)도 이를 미실험 항목으로 명시한다. 기존 실험은 비교한 중앙값·NaN·유형별 처리의 차이가 작다는 사실을 보여 주지만, GAIN 자체의 효과를 분리해 확정하지는 못한다.

**권장 표현:**

> 비교한 중앙값·NaN·유형별 처리의 차이는 작았다. 대회 파이프라인에는 분할 전에 GAIN을 학습하고 타깃을 포함한 문제가 있었지만, GAIN 자체의 효과와 누수의 영향을 분리하려면 fold 안에서 학습한 GAIN과의 통제 비교가 필요하다.

한국어와 영어 README를 함께 수정해야 한다.

### 3.6. 결측치 설명에 논리 오류와 확인되지 않은 가정이 있다

**분류:** 문맥·근거 오류

위치: [`README.ko.md`](../README.ko.md)의 5-4 및 5-7 — 점검 당시 213~215행, 316~317행 부근. 영어 README와 [`docs/experiments/MISSING_TYPES.md`](experiments/MISSING_TYPES.md)의 관련 해석도 함께 검토할 필요가 있다.

#### 영향받는 행 수에 대한 설명

“해당 3개 열이 99% 빈칸이라 영향을 받는 행이 적다”는 설명은 맞지 않는다. 결측값을 1 대신 0으로 채울 때 값이 바뀌는 행은 대부분이다. 적은 것은 실제로 1이 관측된 행이다.

점수 변화가 +0.00018로 작았다는 관측은 맞지만, 그 원인을 결측 비율만으로 확정할 수는 없다.

**권장 표현:**

> 빈칸을 0으로 간주한 처리에서는 AUC가 +0.00018 상승했다. 실제로 1이 관측된 행은 적지만, 개선 폭이 작은 원인은 이 실험만으로 확정할 수 없다.

#### 빈칸의 의미에 대한 가정

어떤 열에서 1만 관측된다는 사실만으로 빈칸이 반드시 “아니오”라고 확정할 수는 없다. [`docs/DATA.md`](DATA.md)에는 공식 데이터 정의서를 확인하지 못했다는 한계도 명시되어 있다.

**권장 조치:** 공식 정의를 확인하기 전에는 “빈칸은 아니오” 또는 “아니오를 예로 채운 버그”라고 단정하지 않고, “빈칸을 0으로 간주한 실험”이라고 표현한다.

## 5. 점검 한계

- 전체 데이터의 튜닝·CatBoost·GAIN 재학습은 수행하지 않는다.
- 구형 파이프라인을 시작부터 제출 파일 생성까지 실행하지 않는다.
- 공개 대회 노트북 전체를 재실행하지 않는다.
- 외부 링크의 접근 가능 여부, 대회 데이터 정의서, 리더보드 수치는 새로 검증하지 않는다.
- 저장된 예측과 요약 지표의 일치는 확인하지만, 이것만으로 학습 과정의 모든 독립성이나 임상적 유효성을 입증하지는 않는다.
- 점검 중 코드·환경·기존 실험 결과를 수정하지 않는다. 이 보고서만 새로 추가한다.
